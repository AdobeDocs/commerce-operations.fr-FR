# ACP2E-4908 : les catalogues volumineux entraînent une utilisation excessive de la mémoire Redis ou Valkey

Le correctif ACP2E-4908 corrige le problème où des catalogues volumineux pouvaient entraîner une utilisation excessive de la mémoire dans [!DNL Valkey] (ou [!DNL Redis]), car des entrées de cache de disposition distinctes étaient créées pour chaque produit dans chaque vue de magasin. Ce correctif est disponible lorsque la version 1.1.83 de [[!DNL Quality Patches Tool (QPT)]](/help/tools/quality-patches-tool/quality-patches-tool-to-self-serve-quality-patches.md) est installée. L’ID du correctif est ACP2E-4908. Notez que ce problème doit être résolu dans Adobe Commerce 2.4.10.

## Produits et versions concernés

**Le correctif est créé pour la version Adobe Commerce :**

* Adobe Commerce (toutes les méthodes de déploiement) 2.4.8-p4

**Compatible avec les versions d’Adobe Commerce :**

* Adobe Commerce (toutes les méthodes de déploiement) >=2.4.8 &lt;2.4.10

>[!NOTE]
>
>Le correctif peut s’appliquer à d’autres versions avec de nouvelles versions de [!DNL Quality Patches Tool]. Pour vérifier si le correctif est compatible avec votre version d’Adobe Commerce, mettez à jour le package `magento/quality-patches` vers la dernière version et vérifiez la compatibilité sur la page [[!DNL Quality Patches Tool] : Rechercher des correctifs](https://experienceleague.adobe.com/tools/commerce-quality-patches/index.html). Utilisez l’ID du correctif comme mot-clé de recherche pour localiser le correctif.

## Problème

Les catalogues volumineux peuvent entraîner une utilisation excessive de la mémoire dans [!DNL Redis] ou [!DNL Valkey], car des entrées de cache de disposition distinctes sont créées pour chaque produit dans chaque vue du magasin.

<u>Procédure à suivre </u> :

1. Configurez [!DNL Valkey] (ou [!DNL Redis]) comme serveur principal du cache par défaut.
1. Modifiez le `app/etc/env.php` et définissez le bloc cache.frontend.default sur :

   ```
   'default' => [
       'id_prefix' => '061_',
       'backend_options' => [
           'server' => 'valkey',          // your Valkey/Redis hostname
           'port' => '6379',
           'database' => '1',
           'password' => '',
           'compress_data' => '0',        // key recipe — leaves XML uncompressed
           'persistent' => 0,
           'read_timeout' => 10,
           'connect_retries' => 2,
       ],
       'backend' => 'redis',
   ],
   ```

   Alors `flush: bin/magento cache:flush`.

1. Générer l&#39;appareil à performance moyenne :

   ```
   bin/magento setup:performance:generate-fixtures \
       setup/performance-toolkit/profiles/ce/medium.xml
   ```


   Cela produit 3 sites web × 3 groupes de magasins × 3 vues de magasin, 24 000 produits simples + 640 produits configurables, 33 ensembles d’attributs, 50 000 commandes. Compter 10 min de trajet sur une machine rapide.

1. Réinitialiser [!DNL Valkey] `db1` et préchauffer :

   ```
   valkey-cli -h <host> -n 1 FLUSHDB
   bin/magento cache:flush
   ```

1. Explorez aux pages de produits dans les magasins. Créez un exemple de liste et accédez à chaque URL :

   ```
   # Build 200 random product URLs across stores 1–4
   mysql -e "SELECT CONCAT(s.code,'|',u.request_path)
             FROM url_rewrite u JOIN store s ON u.store_id=s.store_id
             WHERE u.entity_type='product'
               AND u.request_path NOT LIKE 'catalog/product/%'
               AND s.store_id BETWEEN 1 AND 4
             ORDER BY RAND() LIMIT 200;" magento > urls.txt
   
   while IFS='|' read -r STORE URL; do
       curl -s -o /dev/null "http://<base-url>/${URL}?___store=${STORE}"
   done < urls.txt
   ```

1. Observez l’empreinte du cache `LAYOUT` :

   ```
   valkey-cli -h <host> -n 1 --scan --pattern "*LAYOUT_FRONTEND_STORE*" | wc -l
   valkey-cli -h <host> INFO memory | grep used_memory_human
   ```


   Augmentez l’explore (ou utilisez `large.xml`/`extra_large.xml` et un outil de chargement réel tel que siege/work) pour atteindre le régime de 10 000 clés/1,7 Go du client.

<u>Résultats attendus</u> :

Les performances ne sont pas affectées lorsque la compression est activée.

<u>Résultats réels</u> :

- Les clés `LAYOUT_FRONTEND_STORE` [!DNL Redis] consomment une quantité importante d’espace.
- Sur une nouvelle installation d’appareil de taille moyenne, après 200 accès au produit : environ 564 clés de `LAYOUT_FRONTEND_STORE` et une `used_memory_human` d’environ 20 Mo (par rapport à environ 10 Mo de base avant l’explore) - environ 2,8 clés de cache de mise en page par accès à la page du produit, augmentant linéairement avec les produits uniques visités × les magasins.
